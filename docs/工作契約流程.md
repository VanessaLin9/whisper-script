# 會議錄音 → 逐字稿 → 會議記錄：工作契約流程

**版本：** 0.3  
**適用專案：** `/Users/user/whisper-script`
**最後更新：** 2026-08-07  
**契約狀態：** Codex 清洗模式；LLM API 尚未啟用

> **目前執行者**：語意清洗與專有名詞校正目前由 Codex 直接執行。流程不得假設 LLM API adapter 已存在，也不得在未確認時自行呼叫 API。週末接 API 時，新增 provider/adapter 必須遵守本契約，不得改變既有檔案、state、確認點與 Notion idempotency 規則。

這份文件是 pipeline 的工作契約，不是使用教學。任何人修改單一階段時，都必須保留下游階段看到的輸入格式、檔案命名、狀態欄位與失敗語義；若契約需要變更，先更新版本與遷移說明，再修改程式。

**0.3 實測修訂：** 明確區分「音訊轉錄交接」與 controller 範圍；`full` 在目前版本仍是 deterministic 預清洗＋state handoff，不代表清洗與 Notion 已自動完成；Notion 會議頁必須附加 cleaned TXT，且 state 要保存頁面與附件追溯資訊。

## 1. 契約目標

把每場會議處理成三類可追溯產物：

1. **原始產物**：音訊、Whisper TXT/SRT/JSON；只能讀，不能被任何清洗階段覆蓋。
2. **逐字稿產物**：deterministic 預清洗稿與 Codex 語意清洗稿；保留談話順序與技術細節，不做摘要。
3. **會議記錄產物**：以清洗稿為唯一內容來源，建立一場會議一篇的 Notion 頁面；不得把不同會議合併到同一日誌頁。

## 2. 目前不在契約內的事情

- 不在錄音或轉錄階段自動修正專有名詞；Whisper prompt/vocabulary 是後續工作。
- 不由目前的 controller 自動呼叫 LLM API；目前由 Codex 讀取 prompt note 後執行清洗。
- 不把逐字稿清洗直接變成會議摘要、待辦或工作日誌；那是後續 `standup-worklog` 階段。
- 不在沒有使用者確認時寫入 Notion。
- 不把含 domain knowledge 的本機 prompt note 提交到 Git。

## 3. 固定入口與目錄

| 名稱 | 契約位置 | 說明 |
|---|---|---|
| 會議資料根目錄 | `/Users/user/MeetingRecords` | 主機上的會議 workspace 根目錄；可由 `MEETING_RECORDS_DIR` 覆寫 |
| pipeline controller | `src/meeting_pipeline.py` | 發現、選擇、預清洗、state 與交接 |
| deterministic preparer | `src/postprocessing/preparer.py` | 只做機械性整理，不猜語意 |
| prompt registry | `config/prompt_sources.json` | 只放 key/title/page ID/檔名等 metadata，不放 domain 內容 |
| 私有 prompt notes | `.local/prompt_notes/*.md` | gitignored；每個主題一份完整 prompt/domain note |
| 清洗 skill | `clean-meeting-transcripts` | 清洗規則、保真檢查、術語信心分級 |
| 會議記錄 skill | `standup-worklog` | 清洗稿 → 一場會議一篇 Notion 頁面 |

## 4. 端到端階段契約

每一階段都要有明確輸入、輸出與不可破壞規則。階段必須依序執行；如果某階段失敗，保留前一階段產物，從失敗階段重試。

### Stage -1：錄音／轉錄交接

**目前實作：** `transcribe-english.sh` 與其 organizer；尚未由 `src.meeting_pipeline` 自動呼叫。

- 輸入可以是 `MeetingRecords/Transcripts/<id>.<audio>` 或其他使用者明確指定的本機音訊。
- 若來源尚未有 timestamped workspace，先建立 `YYYY-MM-DD_HHMM_<id>/`，再產生 raw TXT、SRT、JSON 與可選的 normalized audio。
- 會議開始時間的優先順序為：使用者明確指定 > 音訊 metadata > 檔案 metadata；不得把處理當下時間當成會議開始時間。SRT 只能補充時間軸與時長，不能單獨推導日期。
- 轉錄失敗時不得建立「看似完成」的下游 state；保留原始音訊與可診斷錯誤。

### Stage 0：選擇會議與提示詞

**輸入：** `/Users/user/MeetingRecords` 下的 timestamped workspace。  
**互動必問：**

1. 要處理哪一場會議？可用清單編號、meeting ID 或 `YYYY-MM-DD_HHMM`。
2. 使用哪個 prompt profile？目前顯示本機 note front matter 的標題：`inno`、`whisper`，以及明確的 `new/尚未建立`。
3. 使用哪種模式？`full`、`preclean` 或 `handoff`。
4. 最後是否允許 Notion 寫入？這個確認不得被本地檔案處理取代。

**規則：**

- 不可只因資料夾最新就自動選擇會議。
- 未註冊 prompt 不得靜默套用另一份 prompt。
- `.local/prompt_notes/<key>.md` 存在時，讀該檔案；不存在才回到使用者選定的 Notion note。
- 選擇結果必須寫入 pipeline state。
- 目前 `full` 只代表 controller 執行預清洗並建立技能交接 state；清洗、會議記錄與附件仍是明確 hand-off stage。未來接上 adapter 前，不得把 `full` 顯示成「已完成全部流程」。

### Stage 1：輸入驗證與來源保護

**必要來源：**

- 一個 raw `<stem>_transcription.txt`；
- matching `<stem>_transcription.srt`（有則優先提供時間軸）；
- 音訊與 JSON 可作 fidelity reference，但不是清洗輸出必要條件。

**規則：**

- 原始 TXT、SRT、JSON、音訊永遠只讀。
- 同一資料夾若有多份未標記 raw transcript，fail closed，不猜選哪一份。
- 會議時間取自資料夾/檔名與 SRT，不得用處理當下時間替代。
- 時區預設 `Asia/Taipei`。

### Stage 2：deterministic 預清洗

**實作：** `src/postprocessing/preparer.py` 的 `prepare_file`。  
**輸入：** raw TXT。  
**輸出：** `<stem>_transcription_prepared.txt` 與 manifest/statistics。

**允許：** encoding/line ending、空白、明顯 ASR 格式雜訊、相鄰完全重複片段、機械性段落組合。  
**禁止：** 修正 Athena/Asuna 等專有名詞、補寫句意、猜講者、改寫結論、摘要、刪除實質對話。

輸出存在時預設重用並回報 `existing`；只有明確 `--force` 或等價確認才能刷新。此階段不應呼叫網路或 LLM。

### Stage 3：載入 prompt note

**來源優先序：**

1. 使用者在 Stage 0 選定的本機 `.local/prompt_notes/<key>.md`；
2. 該 note 的 Notion source（只讀、只讀取被選定的頁面）；
3. 使用者提供的本機 reference 或貼上的 glossary。

**輸出：** 一份只供本次清洗使用的 prompt context，並在 state 記錄 key、標題、source/page ID、local path。

**規則：**

- 不混用 `inno` 與 `whisper`，除非使用者明確要求。
- prompt note 是證據與候選詞彙，不是把所有近音字無條件替換的白名單。
- 只讀使用者選的 note；不因遇到一個不確定詞就把所有 Notion 搜尋結果載入。
- 私有 note 不得寫回 tracked code、README、公開 log 或 Git。

### Stage 4：Codex 語意清洗（目前的清洗者）

**目前執行者：** Codex，依 `clean-meeting-transcripts` skill。  
**輸入：** prepared TXT、matching SRT、raw TXT（必要時交叉核對）與 Stage 3 prompt context。  
**輸出：** `<stem>_transcription_cleaned.txt`；若目標已存在，先產生 `_v2` 或暫存 replacement，驗證後才可替換。

**必須保留：**

- 時序、問答、修正、不同意見、例子、數字、日期、API、模型設定與技術推理；
- 有意義的重複、不確定性與自我修正；
- 無法確認的專有名詞，以 `[待確認：疑似 XXX]` 或 `[內容不清，需回聽]` 標示。

**可以改善：**

- 標點、斷句、段落、明顯 ASR 碎片、確定的同音錯字與英文大小寫。

**禁止：**

- 摘要、會議記錄標題、決議/待辦抽取；
- 發明講者、背景、結論或技術細節；
- 僅因詞彙表出現就強制替換；
- 把多段問答濃縮成一段結論。

若逐字稿超過約 20–30 分鐘，依 SRT 時間軸切成約 10–15 分鐘區段，保留前後 30–60 秒上下文；只輸出核心區間，合併後檢查接縫。

### Stage 5：清洗品質閘門

清洗稿未通過以下檢查時，不得進入 Notion：

- raw/prepared/cleaned 的開頭與結尾可對照；
- 每個主題轉換與實質問答仍存在；
- 未確認名稱沒有被靜默改成看似合理的名稱；
- 沒有新增「摘要、決策、待辦、結論」等衍生結構；
- 長度基準是實際送進語意清洗的檔案：通常為 `<stem>_transcription_prepared.txt`；只有 prepared 不存在時才用 raw TXT。SRT/raw 用於交叉核對，不作主要長度基準；
- cleaned 若比上述 semantic input 短超過約 20%，停止交付並重新檢查是否誤做摘要；
- 原始音訊、TXT、SRT、JSON、prepared 與 manifest 均未被覆蓋；
- 輸出檔案與使用的 prompt profile 可由 state 追溯。
- Stage 5 必須產生可追溯的品質結果（semantic input、cleaned UTF-8 bytes/字元數、縮減比例、檢查結果與檢查時間）；不能只靠人工口頭判定「通過」。

品質閘門是阻擋錯誤交付的警告，不是要求用填充文字把長度補回去。

### Stage 6：產生會議記錄

**實作：** `standup-worklog` skill。  
**輸入：** 已通過 Stage 5 的 cleaned TXT。  
**輸出：** 一場會議一篇的 Notion 頁面。

內容格式、coverage map、決策／提案分類、owner 證據與未來 LLM prompt／JSON 契約，見 [`meeting-summary-spec.md`](meeting-summary-spec.md)。

**頁面規則：**

- stand-up 使用 `Stand-up｜YYYY/MM/DD HH:mm`；其他會議使用 `會議記錄｜YYYY/MM/DD HH:mm`。
- 內容包括時間、來源、進度、下一步、阻塞/風險、決策/依賴與待確認；只寫逐字稿支持的資訊。
- 不把會議內容塞到 `工作日誌 - YYYY/MM/DD` 聚合頁。
- 同一天兩場會議必須是兩篇獨立頁面。
- Notion 寫入前要有確認；寫入後重新 fetch 驗證標題、時間、區塊與是否重複。
- 會議頁內容與 cleaned TXT 附件都屬 Notion 寫入；同一次確認涵蓋兩者。若 cleaned TXT 含尚未完成遮蔽的敏感資訊，必須先停在 pending，不得因附件是檔案就繞過隱私確認。

### Stage 7：附件與追溯

每次建立會議記錄時，必須把該場的 cleaned TXT 以 Notion file block 附加到同一篇會議頁；raw TXT、SRT 或其他產物可依使用者要求附加。附件不是清洗輸入的替代品，也不得修改原始檔。

- 上傳檔名使用實際 cleaned 產物檔名（例如 `<stem>_transcription_cleaned.txt`）。
- 上傳成功後，立即把 file block 寫入頁面，並重新 fetch 確認附件存在；不可只在頁面放本機路徑。
- 若附件上傳或附加失敗，Notion stage 必須保持 pending，保留本機清洗稿並回報可重試的錯誤。

State、Notion page URL、source paths、prompt profile 與未解決詞彙要能回到同一場 meeting workspace。

Notion retry 必須以 meeting key＋cleaned source hash＋附件檔名/ hash 做 idempotency；建立頁面成功但附件失敗時，只能補附件，不得重建第二篇會議頁。

## 5. 檔案命名與不可變界面

對 `YYYY-MM-DD_HHMM_<id>/` workspace，以下名稱是下游界面：

```text
<stem>_transcription.txt              # raw，唯讀
<stem>_transcription.srt              # timeline，唯讀
<stem>_transcription.json             # ASR metadata，唯讀
<stem>_transcription_prepared.txt     # Stage 2
<stem>_transcription_prepared.txt.manifest.json
<stem>_transcription_cleaned.txt      # Stage 4 output
<stem>_pipeline_state.json               # controller state
```

任何新階段應新增檔案或欄位，不得任意改名、刪除或讓既有欄位改變型別。若確實需要改名，提供 migration 或兼容讀取，不得只改 producer。

```json
  },
  "prompt_profile": {
    "name": "inno",
    "label": "inno｜Inno Group／AI Team",
    "source": "...",
    "local_path": ".local/prompt_notes/inno.md"

      "preclean": "completed|pending",
      "clean_transcript": "completed|pending",
      "notion_worklog": "completed|pending"
    },
    "next_stage": "clean_transcript",
    "quality_result": {
      "status": "pending|passed|failed",
      "semantic_input": "...",
      "cleaned_bytes": null,
      "semantic_input_bytes": null,
      "reduction_ratio": null,

    "notion_worklog_result": {
      "status": "pending|page_created|attachment_attached|completed|failed",
      "page_url": null,
      "page_id": null,
      "transcript_attachment": {
        "status": "pending|attached|failed",
        "filename": null,
        "source_hash": null,

    "clean_skill": "clean-meeting-transcripts",
    "worklog_skill": "standup-worklog",

```

狀態規則：

- stage 狀態只能在完成驗證後由 `pending` 變 `completed`；
- 失敗時保留前一階段 `completed`，不要偽造下一階段完成；
- 已有 state 預設 fail closed；刷新必須明確使用 `--force-state`；
- 下一個實作增量必須加入 raw/prepared/cleaned hashes、prompt revision、model/provider、品質結果、Notion page ID、附件 hash 與 attempts；保留現有欄位語義；
- state 不得存 API token、完整 prompt body 或完整逐字稿內容。

## 7. 目前實際啟動方式

在已完成轉錄、且 workspace 位於 `/Users/user/MeetingRecords` 後：

```bash
cd /Users/user/whisper-script
PYTHONPATH=. python3 -m src.meeting_pipeline
```

controller 會依序詢問會議、prompt profile、流程與確認。完成轉錄交接後，`full` 目前只做到 Stage 2 預清洗與 state；Codex 接手 Stage 3–5，完成清洗後再執行 Stage 6–7 的會議記錄、cleaned TXT 附件與 Notion 驗證。

## 8. 修改任何階段前的契約檢查

修改前先回答：

1. 這個階段的輸入檔名、格式與來源是否不變？
2. 原始檔是否仍然唯讀？
3. 下游能否仍用相同的 prepared/cleaned/state 路徑？
4. prompt key/title/source/local path 是否仍可追溯？
5. 失敗是否 fail closed，且可以從該階段重試？
6. 是否新增了未經確認的語意、術語或 Notion 寫入？
7. 是否補了 unit/integration test 與文件？

若答案是否定，先更新本契約的版本、受影響階段與 migration，再提交程式修改。

## 9. 後續 API adapter 的接入界線

週末接 API 時，只能替換 Stage 4 的執行者：

```text
Codex manual cleaner  →  LLM adapter
```

不得改變：

- Stage 0 的使用者選擇與確認；
- Stage 2 prepared 輸入與原始檔保護；
- Stage 3 prompt note key/title/source/local path；
- Stage 5 的長度、保真、未確認詞彙與 no-summary 閘門；
- Stage 6 的一場會議一篇 Notion page 與 idempotency。
- Stage 7 的 cleaned TXT 附件、隱私確認、附件 idempotency 與失敗可重試語義。

API adapter 必須先在本機 dry-run、mock provider 與失敗重試測試通過，再加入 controller 的可選模式；不能因為 API 暫時不可用而阻塞目前的 Codex 清洗流程。

## 10. 完成判定

一場會議只有在以下條件都滿足時才算完成：

- raw、SRT、prepared 與 cleaned 產物仍可追溯；
- cleaned transcript 通過 Stage 5；
- 使用的 prompt profile 與時間 metadata 已記錄；
- 若要求會議記錄，Notion 有且只有一篇對應會議頁；
- 該頁面已附加同一場的 cleaned TXT，且附件可由 page fetch 驗證；
- Notion 頁面沒有誤寫入同日聚合工作日誌；
- 未確認專有名詞與清洗限制已向使用者說明；
- 任何失敗都保留本機產物與可重試狀態。
